# Proof of work

This document is a direct, honest account of what SignalFlow is and is not. It
exists so a reviewer can verify the claims quickly and calibrate trust. The
project is a deterministic, demo-safe architecture platform, not a live
production SaaS, and the sections below say exactly where that line sits.

## What SignalFlow proves

- A layered architecture with enforced boundaries: pages render, services
  compose, repositories own data access, and pure engines hold deterministic
  domain logic. The boundary rules are checked in CI, not just described.
- Deterministic domain engines for intent and opportunity scoring, action
  graph planning, workflow orchestration, outcome classification, and revenue
  attribution. Identical input yields identical output, with no randomness and
  no model calls.
- Provider governance that treats external providers as future-ready
  definitions while selecting only internal mocks in demo mode.
- Human-in-the-loop governance: AI recommendations and sensitive voice plans
  are routed through a review queue, and the state machine prevents executing
  work that still needs review.
- Multi-tenancy: the organization id always comes from the resolved server
  context, never from the client.
- An end-to-end audit trail, revenue attribution, and a voice simulation
  platform, all behind a consent and compliance policy layer.

## What is intentionally simulated

- All communication. No SMS, email, or voice call is ever sent. Calls and
  messages are simulated by deterministic engines and internal mock providers.
- All AI output. Recommendations, confidence scores, and explanations are
  produced by deterministic logic, not an external model.
- Customer data. Customers, signals, and opportunities are generated by a
  seeded synthetic data generator, so scenarios are believable and repeatable.
- Outcomes and revenue. Outcome events and attributed revenue are derived from
  fixed rules over the simulated workflow, not from real transactions.

## What is not integrated

- No external provider SDKs are installed. The registry names providers such as
  OpenAI, Anthropic, Gemini, ElevenLabs, Twilio, and SendGrid as future-ready
  definitions only. None of their SDKs are a dependency.
- No provider API calls and no outbound network calls are made by the
  application code.
- No real provider credentials or secret environment variable names exist in
  the repository.

## How provider safety is enforced

- The provider selection engine resolves an internal mock for every capability
  when the live feature flags are blocked, which is the demo-mode default.
- The safety scan (`npm run scan:safety`) fails the build if banned content
  appears: provider SDK package names, real secret environment names, network
  call patterns, attribution footers, or em dashes.
- Tests in `tests/provider-governance-proof.test.ts` prove the registry ships
  external definitions while demo mode never selects them.

## How architecture boundaries are enforced

- The architecture check (`npm run check:architecture`) fails the build when a
  page imports a repository directly, or when a pure engine imports React,
  Prisma, the Prisma singleton, Clerk, Next, a repository, or a provider SDK.
- This keeps the page to service to repository to engine flow honest over time
  rather than relying on review discipline alone.

## How to validate the repo locally

Run the same gates CI runs:

```bash
npm install
npm run typecheck          # TypeScript, no emit
npm run lint               # Next.js and ESLint
npm run test               # Vitest, deterministic engine and proof tests
npm run scan:safety        # bans SDKs, secrets, network calls, em dashes
npm run check:architecture # enforces layer boundaries
npx prisma validate        # schema validation, no database needed
npm run build              # production build
```

A placeholder `DATABASE_URL` is enough for typecheck, lint, tests, the scans,
prisma validate, and build. None of those steps connect to a database.

## What a recruiter should look at first

1. `docs/REVIEWER_EXPERIENCE.md`, then click `Run the 60-second demo` from the
   landing page.
2. The landing page scenario showcase, which walks three real-world stories
   (automotive retail, dental recall, life insurance book expansion) into a
   seven-step drill-down.
3. This document, to see what is real and what is simulated.

## What a hiring manager should inspect

- `npm run check:architecture` and `npm run scan:safety`, then read
  `scripts/check-architecture-boundaries.ts` and `scripts/scan-safety.ts` to
  confirm the guarantees are mechanical, not aspirational.
- The `tests/` folder, especially the proof tests: tenant isolation, human
  review gating, provider governance, and revenue attribution. These assert
  business behavior, not snapshots.
- The pure engines under `lib/` (scoring, action graph, outcomes, attribution,
  review, voice), which carry no framework imports.
- `docs/TECHNICAL_DEBT_REGISTER.md`, which separates portfolio readiness from
  true production readiness.

## What remains before production readiness

- Replace internal mock providers with real, governed integrations behind the
  existing feature-flag and readiness framework. The seams exist; the live
  paths do not.
- Add a test database in CI to cover services and repositories, not only the
  pure engines.
- Add server-side caching or precomputed snapshots for the heavy dashboard and
  command center reads.
- Define and test a deployment-specific Content-Security-Policy, which is
  deferred today to avoid shipping a brittle header that breaks rendering.
- Upgrade the web framework to clear the current upstream dependency advisories
  surfaced by the CI dependency audit.

This list is deliberately honest. SignalFlow is a strong architecture and
governance proof. It is not a live production system, and it does not pretend to
be one.
