# Screenshot Checklist

The screenshots that best show SignalFlow, with what each should show, why it
matters, and recommended framing. Capture at a desktop width with the demo data
seeded so the pages are full.

## Landing page

```text
Show:    the hero positioning, the not-just-a-CRM section, and the demo safe note.
Why:     it sets the product story and the honest demo posture.
Framing: full width hero, top of the page, light or dark consistent with the app.
```

## Revenue Command Center

```text
Show:    the hero summary sentence, the executive metric cards, and the revenue
         lifecycle row.
Why:     it is the flagship one-screen story of the product.
Framing: capture from the section heading through the lifecycle row.
```

## Mission Replay

```text
Show:    the ordered timeline from signal to revenue and the what this proves card.
Why:     it demonstrates a full deterministic lifecycle for one customer.
Framing: capture the timeline with several steps visible.
```

## AI Center

```text
Show:    a recommendation with its confidence score, tier, and explanation.
Why:     it proves explainable AI output rather than a black box.
Framing: a single recommendation detail or two cards in the grid.
```

## Review Queue

```text
Show:    recommendations grouped by review state and the voice plans needing
         review card.
Why:     it proves a human-in-the-loop governance gate.
Framing: include at least two review state groups.
```

## Voice Command Center

```text
Show:    the simulated banner, the metric cards, and the compliance breakdown.
Why:     it proves an honest simulated voice operations layer.
Framing: capture the banner and metrics together so the simulated label is visible.
```

## Voice Replay

```text
Show:    the simulated transcript and the compliance and outcome cards.
Why:     it proves deterministic transcript generation and outcome mapping.
Framing: include the simulated badge and a few transcript lines.
```

## Provider Management

```text
Show:    the all live providers disabled banner, the capability matrix, and the
         feature flags.
Why:     it proves a provider safety model with everything disabled.
Framing: capture the banner and the capability matrix together.
```

## Provider Sandbox

```text
Show:    one capability card with the selected mock provider, the blocked live
         reason, and what live use would require.
Why:     it proves a sandbox that makes no network call.
Framing: a single capability card is enough.
```

## Executive Insights

```text
Show:    influenced revenue, revenue leaks, and AI governance metrics.
Why:     it proves a leadership view composed from the platform.
Framing: capture the top metrics and one insight section.
```

## Architecture docs

```text
Show:    a text diagram from docs/ARCHITECTURE_OVERVIEW.md, for example the
         signal to revenue lifecycle or the service and repository architecture.
Why:     it gives technical reviewers a quick mental model.
Framing: a clean code block screenshot or a rendered markdown view.
```
